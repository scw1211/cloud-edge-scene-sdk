# 系统全模块介绍与答辩讲解

本文用于帮助项目负责人完整理解并讲清楚这套系统。重点不是逐行解释代码，而是说明每个模块解决什么问题、输入输出是什么、模块之间如何协作，以及答辩时应怎样准确表述项目贡献。

## 一、先用一句话说明作品

> 我做的不是一个交通预测模型，而是一套可以接入交通、工业等不同业务的分布式感知、边缘自治、云端融合、动态调度和一致性决策系统。ASTGCN、Student、Edge-Qwen、ExtraTrees和云端9B都是其中的模型组件，真正的主体是场景插件化的云边协同框架和完整运行闭环。

系统主链如下：

```text
场景原始数据
  → 场景专用感知模型
  → 统一语义事件 SemanticEvent
  → 边缘规则 / Student / Edge-Qwen
  → provisional 本地临时结果
  → 轻量摘要经持久 Outbox 上云
  → 云端汇聚多个边缘的信息
  → ExtraTrees 等专业模型生成轻量 final
  → 少量疑难事件可调用云端9B复核
  → 冲突检测、安全约束和动作协调
  → final 回填边缘并形成纠错反馈
```

系统把三个容易混淆的问题拆成三条独立链路：

1. 模型路由：规则、Student、Edge-Qwen或云端9B谁来判断；
2. 证据路由：上传摘要、压缩特征还是局部原始数据；
3. 动作授权：动作能否本地执行，还是必须等待完整云确认。

## 二、公共协议与场景插件

### 1. 外部事件信封

`cloud_edge_framework/event_envelope.py`定义外部`SceneEventEnvelope`。框架只固定事件身份和路由字段：

- `id`、`source`、`type`；
- `scene`、`edgeid`；
- `time`、`dataschema`；
- 场景自行定义的`data`。

因此工业可以在`data`中传异常分数、热力图和工件编号，交通可以传道路区域摘要，电力可以传负荷和设备状态。公共框架不会把工业示例中的字段强制到所有场景。

### 2. 统一语义事件

`cloud_edge_framework/contracts.py`定义内部`SemanticEvent`，主要包含：

- `scope`：实体、区域、时间窗、关联键和共享资源；
- `prediction`：场景模型预测、置信度和概率；
- `risk`与`uncertainty`：业务后果和模型不确定性；
- `timing`：预处理、边缘推理耗时和业务时限；
- `evidence`：摘要、特征和原始证据；
- `candidate_actions`：场景允许提出的动作；
- `scene_payload`和`metadata`：场景信息与内部调度提示。

它是交通、工业和其他场景进入公共云边流程后的共同语言。

### 3. 场景插件

`cloud_edge_framework/plugins/base.py`定义插件接口。每个场景主要实现：

- `normalize()`：把原始业务结果转换为`SemanticEvent`；
- `edge_decide()`：产生本地初判；
- `cloud_decide()`：产生云端专业判断；
- `prepare_cloud_event()`：裁剪真正允许上传的数据；
- `fuse_cloud_context()`：融合相邻边缘上下文；
- `action_conflict()`和`resolve_action_conflict()`：定义本场景的冲突和解决方法。

`registry.py`负责根据场景、事件类型和`dataschema`选择插件；`plugin_manager.py`负责插件热重载和运行快照切换。

## 三、边缘与云端运行时

### 4. 边缘运行时

`cloud_edge_framework/runtime.py`中的`EdgeRuntime.process()`是边缘主编排器。一条事件进入后依次完成：

1. 外层信封与场景Schema校验；
2. 查找并调用场景插件；
3. 转换统一语义事件；
4. 运行场景本地决策；
5. 执行动作安全检查；
6. 规划证据等级；
7. 获取网络与历史性能状态；
8. 选择本地、同步云或异步云路径；
9. 返回`provisional`结果；
10. 将需要上云的事件持久化；
11. 记录决策生命周期、通信量和分阶段时延。

`edge_service.py`把这些能力包装为独立HTTP服务。正式交通部署中，边缘框架服务通常监听18101，Edge-Qwen的`llama-server`监听18190。

### 5. 云端运行时

`CloudRuntime`和`cloud_service.py`负责：

- 接收边缘标准事件；
- 云端幂等去重；
- 多边缘持久汇聚；
- 调用场景云端专业模型；
- 进行全局上下文融合；
- 检测和协调动作冲突；
- 生成权威最终结果；
- 接收边缘反馈并保存纠错数据。

云端的作用是补充边缘缺少的全局信息，不是每次都代替边缘重新判断。

## 四、动态调度与网络感知

### 6. 网络状态监测

`networking.py`由边缘主动测量云端可达性、RTT、抖动和丢包；调用方不能通过请求参数伪造“当前网络良好”。`performance.py`按场景、证据等级和网络档保存历史成功率、时延和字节EWMA。

### 7. 计算路径调度

`scheduling.py`综合：

- 业务时限；
- 模型不确定性；
- 是否存在分歧或冲突；
- 当前网络状态；
- 预计通信量；
- 历史云路径时延；
- 场景是否明确要求云确认。

四条公共路由为：

| 路径 | 含义 |
| --- | --- |
| `edge_only` | 本地结果直接完成 |
| `cloud_async` | 立即返回临时结果，摘要后台上云 |
| `cloud_sync` | 业务明确要求完整云确认且预算允许时等待 |
| `local_autonomy` | 云不可用时进行受约束的本地自治 |

对于声明了多边缘汇聚的事件，每个样本的轻量摘要都会让云端可见。调度控制的是是否等待、是否升级证据和是否调用大模型，而不是是否让云知道该样本。

### 8. 学习式效用路由

`utility_routing.py`把升级决策表示为：

```text
预计纠错收益 - 推理时延成本 - 通信成本 - 资源成本
```

路由器支持`shadow`和`active`模式。真实反馈不足时只做影子评估，不直接接管线上路径；通过门禁后才允许主动路由。

## 五、证据与通信

### 9. 分层证据规划

`evidence.py`把证据分成：

- `summary`：风险、置信度和少量统计量；
- `feature`：热力图、嵌入、压缩时序等任务特征；
- `raw`：局部原始图像、时序或对象存储地址。

正常事件只发送摘要。模型不确定、证据不完整、节点分歧、场景显式请求或监测失效时才升级证据。

### 10. 大证据文件管理

`artifacts.py`支持真实文件上传、内容长度和SHA-256校验、内容类型检查、相同证据去重保存，以及实际请求和响应字节统计。因此报告中的通信量可以来自真实传输，而不是估算值。

## 六、可靠传输和故障恢复

### 11. SQLite Outbox

`reliability.py`和`replay.py`实现正式边缘到云端的持久队列，支持：

- enqueue、claim、lease、ack和release；
- 多线程互斥；
- 指数退避；
- 进程重启恢复；
- 网络恢复自动补传；
- 队列状态和失败原因统计。

事件先可靠写入SQLite，再由后台发送，因此边缘服务或网络中断不会让待上云事件凭空消失。

### 12. 幂等处理

系统同时校验事件身份、业务上下文、请求摘要和幂等键。完全相同的重试返回第一次结果；相同幂等键对应不同内容时拒绝请求。这解决了“云端已经处理，但响应丢失，边缘再次发送”导致动作重复执行的问题。

### 13. 文件桥接

`file_bridge.py`用于兼容原有识别程序。旧场景只需把完整JSON原子写入目录，文件桥负责稳定性检查、双Schema校验、证据检查、持久排队、发送、重试、成功归档和非法文件隔离。

这样场景识别程序不必与公共框架安装在同一个Python环境。

## 七、多边缘汇聚和最终回填

### 14. 持久化汇聚

`aggregation.py`按照场景提供的关联键、成员名称、预期成员、最小成员数和超时时间汇聚事件。交通使用数据集、数据划分和`sample_id`构成关联键，但公共框架没有把`sample_id`写死。

### 15. 完整结果与部分结果

汇聚状态包括：

- `waiting`：成员尚未到齐；
- 完整`final`：全部预期成员到齐；
- `partial_final`：超时后只有部分成员；
- `local_only_timeout`：没有形成可用云结果。

部分结果会明确标记`evidence_complete=false`和`global_confirmation=false`，不能授权必须完整云确认的动作。

### 16. 迟到成员和有界回填

迟到成员到达后，云端会重开汇聚组、增加结果版本并重新协调。普通Outbox到期后可以正常结束，独立的低频reconciliation队列在有限时间内继续查询新版本：完整结果出现就升级原生命周期，否则到期自动清理。

这个设计同时避免了结果永久停留在2/4，也避免队列无限增长。

## 八、决策生命周期和指标

### 17. provisional到final

`review_tracking.py`持久记录：

```text
边缘临时判断
  → queued
  → inflight
  → 云端首次接收
  → 轻量最终结果
  → 可选大模型复核
  → 是否修正边缘判断
```

系统分别统计：

- 本地临时结果时延；
- 云端首次接收时延；
- 轻量融合最终时延；
- 大模型复核与修正时延；
- 云端修正率。

`cloud_receipt`使用跨机器时间，正式报告必须同时提供NTP/chrony偏差；HTTP RTT使用边缘本机单调时钟，不依赖跨机时钟同步。

### 18. 监测与反馈

`monitoring.py`计算ECE校准误差、预测集合覆盖率、平均集合大小和PSI漂移，并在监测失效时强制复核。`feedback.py`保存边缘初判、云端最终结果和修正信息，为Student、defer gate、Edge-Qwen和效用路由器提供后续训练数据。

## 九、冲突检测与安全执行

### 19. 冲突检测

`conflicts.py`不会因为两个模型预测不同就直接判为控制冲突。只有事件时间相关、业务范围相关、动作影响相同共享资源且动作类型或参数不兼容时，才进入协调。

系统同时记录初始冲突、冲突原因、调整动作、残余冲突和解决成功率。因此“协调后残余冲突为零”不能脱离初始冲突数量单独报告。

### 20. 确定性安全策略

交通`safety_filter.py`负责动作白名单、控制目标权限、参数上下限、非法参数裁剪、重复动作合并、离线权限和异常回退。模型只能提出候选动作，最终是否允许执行由确定性安全逻辑决定。

现有ExtraTrees和冲突协调可以称为“全局信息融合与一致性协调”，不能直接称为“交通全局最优”。全局最优仍需要SUMO/MPC和明确的总旅行时间、排队或吞吐目标实验。

## 十、交通感知与决策模块

### 21. PEMS08与ASTGCN

`traffic_system/traffic_perception_runtime.py`常驻加载真实交通模型。ASTGCN建模道路图的空间联系、时间周期和近期变化，输出未来交通状态及节点/区域风险。

项目没有声称发明ASTGCN，而是在开源ASTGCN基础上完成真实权重接入、风险输出、Jetson推理、四分区事件生成、云边协同接口以及实际时延和资源测量。

### 22. METIS四区域划分

道路图被划分成四个区域。学校部署中：

- Orin Nano A处理分区0、1；
- Orin Nano B处理分区2、3；
- 云端汇聚四个区域结果。

这体现的是多边缘分布式感知，而不是一个板子顺序模拟全部节点。

### 23. 风险标签与校准

交通风险标签使用FCM等方法构建弱标签，并使用温度缩放、APS预测集合、类别条件阈值和conformal覆盖率表达不确定性。FCM标签可用于训练和开发，但不能当成人工交通风险真值。

### 24. 交通Student

`edge_student.py`是交通场景专用的小型决策器。它根据区域预测、节点风险、置信度、拓扑摘要和历史变化产生候选动作。Student不属于公共框架，工业场景不需要复制交通Student，可以使用自己的规则、小模型或其他本地决策器。

### 25. defer gate

`defer_gate.py`判断的不是“道路风险高不高”，而是当前局部信息是否足以支持可靠决策。其输入包括Student置信度、预测集合、Student与规则分歧、证据完整度和预计纠错收益。

### 26. Edge-Qwen 0.8B

交通Edge-Qwen基于Qwen3.5 0.8B，采用场景LoRA、Q6_K GGUF和llama.cpp CUDA运行时。模型输入是最多16个token的紧凑态势编码，输出一个动作token，关闭thinking并经过动作白名单解码。

当前角色消融没有证明它稳定优于规则和Student，因此正常路径不会为了展示大模型而强行调用。它作为少量疑难样本的候选增强器，并保留压缩、量化、发布和后续纠错蒸馏的研究接口。

### 27. 五类语义拆分

`freeway_traffic_full/plugin_impl.py`将原来容易混用的风险含义拆成：

| 语义 | 作用 |
| --- | --- |
| 区域交通状态 | 描述拥堵程度 |
| 动作安全风险 | 决定动作授权等级 |
| 模型不确定性 | 判断当前模型是否可信 |
| 升级预计收益 | 判断更强模型是否可能纠错 |
| 证据完整度 | 判断是否需要追加证据 |

Edge-Qwen和云端9B不再由最大节点业务风险直接触发。

### 28. 特征编码和云端ExtraTrees

`tree_feature_codec.py`把结构化交通摘要转换为冻结顺序的模型特征，并记录特征Schema和模型绑定摘要；`ultracompact_codec.py`生成Edge-Qwen的短态势编码。

云端`cloud_coordinator.py`和ExtraTrees模型融合四个区域摘要、拓扑、Student结果、置信度和相邻区域状态，是正常在线路径的轻量final生成器。

### 29. 云端Qwen3.5 9B

云端9B只处理分歧、复杂证据、专业模型置信度不足或需要解释的少量事件。输出必须经过严格JSON和动作Schema校验；超时、格式错误或运行异常时保留ExtraTrees专业基线，不允许大模型错误覆盖正常结果。

## 十一、Edge LLM模型生命周期

`edge_llm_factory/`覆盖：

```text
锁定国产开源基座
  → 导出纯文本快照
  → 通用蒸馏候选
  → 场景SFT/LoRA
  → 未见集评估
  → LoRA合并
  → GGUF转换和量化
  → Jetson TTFT/内存测试
  → 发布门禁
  → 原子切换和失败回滚
```

它不仅解决训练问题，还管理模型身份、数据集身份、测试集隔离、文件哈希、运行配置、活动版本和回滚历史。通用蒸馏候选目前尚未达到题目要求，不能用交通动作准确率替代数学、代码和自然语言能力指标。

## 十二、部署、资产和测试

### 30. 资产分发

`asset_catalog.json`锁定真实模型文件的版本、大小、SHA-256和下载地址。小型权重随Git发布；629MB Edge-Qwen GGUF和73MB PEMS08推理数组从独立Release下载。安装器不允许使用空文件或假权重绕过验证。

### 31. 从零部署

`deploy_node.py`、`bootstrap_traffic_node.sh`和systemd脚本负责：

- 创建云端和Jetson独立环境；
- 使用与JetPack匹配的NVIDIA PyTorch；
- 编译CUDA版llama-server；
- 下载并校验真实资产；
- 启动云服务、边缘服务和模型服务；
- 执行健康检查和双边缘四分区核验。

### 32. 验收体系

当前发布版本包含：

- 公共框架测试41/41；
- 交通测试18/18；
- 交通冒烟链路；
- 角色分离全链路验收8/8；
- provisional到final故障矩阵7/7；
- 路由、风险通道和Edge-Qwen角色消融；
- 分组bootstrap置信区间；
- 通信量、分层时延和内存统计。

## 十三、工业场景当前边界

仓库已经包含RGB和红外PatchCore/TensorRT/CUDA运行时、特征库压缩、TensorRT引擎构建、Jetson离线部署和验收脚本。

但当前应准确表述为：工业感知运行时和接入基础已经进入仓库，工业场景的完整SemanticEvent插件、双模态云融合、动作映射和学校实测还没有达到交通场景同等完整度。交通是当前完整主场景，工业是第二场景的工程基础。
