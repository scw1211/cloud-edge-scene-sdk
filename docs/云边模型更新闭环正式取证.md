# 云边模型更新闭环正式取证

这套工具用于真实验证以下链路：

```text
云端发布旧版和候选模型
  → 边缘通过 HTTP 拉取完整资产
  → 逐文件校验 SHA-256 和字节数
  → 原子发布下载目录
  → 边缘真实启动旧版、候选版并触发受控失败
  → 边缘自动回滚并重新启动旧版
  → 边缘通过 HTTP 回传正式回执
  → 云端持久保存回执并返回确认
```

它是在既有本地更新状态机外增加的真实云边传输和确认层，不修改场景插件，也不
涉及工业代码。正式运行必须使用两台机器：云地址不能是 `localhost` 或
`127.0.0.1`。

## 文件和职责

| 文件 | 职责 |
|---|---|
| `edge_llm_factory/distributed_update_evidence.py` | 云端 HTTP 发布服务、边缘下载校验、回执和证据生成 |
| `edge_llm_factory/update_loop_evidence.py` | 边缘侧真实的 package→release→apply→rollback 执行器 |
| `edge_llm_factory/serve_release.py` | 启停真实 llama-server、健康检查、推理探针和失败回滚 |
| `scripts/measure_distributed_model_update_loop.py` | 双机取证命令入口 |
| `scripts/evaluate_competition_targets.py` | 七项统一门禁；第 7 项同时检查本地和分布式证据 |

公共命令也可以写成：

```bash
python -m edge_llm_factory measure-distributed-update-loop cloud ...
python -m edge_llm_factory measure-distributed-update-loop edge ...
```

## 正式运行前提

1. 云端和边缘必须位于同一 Git 提交，工作区必须干净。
2. 分布式 runner 和命令入口必须已经纳入该 Git 提交；未提交的源码不能生成正式
   证据。
3. 旧版和候选版必须分别具备合法的 base manifest、adapter package 和不同的
   GGUF；两版决策协议必须兼容，发布门槛必须全部通过。
4. 边缘必须有真实 `llama-server`，并且取证端口未占用、机器上没有另一套
   `llama-server`。脚本不会触碰正式服务。
5. 云端存储目录、边缘输出目录和共享密钥必须放在 Git 仓库之外。
6. 云端和边缘各自准备一个内容完全相同、至少 32 字节的密钥文件。密钥只用于
   HMAC 完整性校验；HTTP 本身不加密，因此应在可信局域网或 VPN 中运行。

## 第一步：云端启动发布与回执服务

以下路径均替换为云端真实路径。`storage-dir` 必须是一个专用于本次 `run-id` 的
新目录；同一目录重启时会复用原发布 nonce 和时间戳，保证清单不变化。

```bash
cd /path/to/cloud-edge-scene-sdk

python scripts/measure_distributed_model_update_loop.py cloud \
  --repository-root "$PWD" \
  --git-commit "$(git rev-parse HEAD)" \
  --old-base /assets/old/base_manifest.json \
  --old-package /assets/old/adapter_package \
  --old-artifact /assets/old/edge-old.gguf \
  --candidate-base /assets/candidate/base_manifest.json \
  --candidate-package /assets/candidate/adapter_package \
  --candidate-artifact /assets/candidate/edge-candidate.gguf \
  --old-release-id edge-model-v1 \
  --candidate-release-id edge-model-v2 \
  --run-id update-20260809-001 \
  --expected-edge-id edge-138 \
  --expected-hardware-id orin-nano-138 \
  --expected-dataset-id update-smoke-v1 \
  --storage-dir /data/evidence/update-20260809-001-cloud \
  --shared-secret-file /data/secrets/model-update-hmac.key \
  --host 0.0.0.0 \
  --port 19300
```

成功启动后会打印 `status=serving`、`publication_sha256` 和监听地址。云端提供四类
接口：

| 接口 | 用途 |
|---|---|
| `GET /api/v1/model-updates/{run_id}/manifest` | 返回带 HMAC 的不可变发布清单 |
| `GET /api/v1/model-updates/{run_id}/files/{file_id}` | 下载清单中的单个文件 |
| `POST /api/v1/model-updates/{run_id}/receipts` | 接收并持久保存边缘正式回执 |
| `GET /api/v1/model-updates/{run_id}/status` | 查询云端是否已收到边缘确认 |

云端在每次下载前重新计算源文件 SHA。如果发布后文件发生变化，下载会立即失败，
不会继续发送被修改的资产。

## 第二步：边缘执行完整闭环

`cloud-url` 必须填云端机器的真实局域网或 VPN 地址。`output-dir` 必须不存在。

```bash
cd /path/to/cloud-edge-scene-sdk

python scripts/measure_distributed_model_update_loop.py edge \
  --repository-root "$PWD" \
  --git-commit "$(git rev-parse HEAD)" \
  --cloud-url http://192.168.31.160:19300 \
  --run-id update-20260809-001 \
  --edge-id edge-138 \
  --hardware-id orin-nano-138 \
  --dataset-id update-smoke-v1 \
  --shared-secret-file /data/secrets/model-update-hmac.key \
  --llama-server /path/to/llama-server \
  --llama-port 19290 \
  --context-tokens 128 \
  --threads 4 \
  --gpu-layers 99 \
  --startup-timeout-seconds 90 \
  --http-timeout-seconds 120 \
  --min-available-memory-mb 1500 \
  --probe-prompt '固定的合法短输入' \
  --output-dir /data/evidence/update-20260809-001-edge
```

下载使用 `.part` 临时文件。每个文件写完后执行 `fsync`、校验 SHA 和字节数，再
原子改名；所有文件和两个 package 再校验一次后，整个下载目录才会原子发布。
下载中断或文件损坏时，最终缓存目录不会出现。

边缘随后调用既有正式状态机，并真实执行：

```text
旧模型启动并完成 health + 1-token 推理
→ 候选模型启动并完成 health + 1-token 推理
→ 注入候选通过后的受控门禁失败
→ CAS 回滚
→ 旧模型重新启动并再次完成 health + 1-token 推理
→ 三个隔离进程全部退出且端口释放
```

只有本地正式证据全部成立，边缘才会构造回执。回执绑定 Git、数据集、硬件、两版
模型、每个下载文件、四阶段证据 SHA 和云端发布 nonce。云端使用共享密钥验证
HMAC 后原子写入回执库，再返回同样带 HMAC 的确认。

## 幂等和失败行为

- 相同 `edge_id + run_id` 重发完全相同的回执：云端返回第一次持久化的同一确认，
  revision 不增加。
- 相同 `edge_id + run_id` 发送不同内容：HTTP 409，旧回执不被覆盖。
- 发布服务用同一存储目录重启：必须生成逐字节相同的发布清单，否则拒绝启动。
- 边缘下载缓存存在且完整：重新校验全部文件后复用，不重复下载。
- 任何正式步骤失败：只保留 `FAILED_NOT_FORMAL_DISTRIBUTED_EVIDENCE.json`，不会
  生成正式完成标记。
- 单元测试使用 `execution_mode=test_http/test_double`，正式边缘和统一门禁都会拒绝
  这些结果。

## 正式输出

边缘成功后，输出目录至少包含：

| 路径 | 内容 |
|---|---|
| `downloads/{publication_sha256}/` | 经逐文件校验并原子发布的旧版、候选版完整资产 |
| `local_execution/` | 本地 package、release、apply、rollback 四阶段原件 |
| `edge_receipt.json` | 边缘发送给云端的完整回执 |
| `cloud_ack.json` | 云端 HTTP 确认和边缘 HMAC 校验结果 |
| `distributed_model_update_loop.json` | 云发、下载、本地执行、回执、确认的总证据 |
| `FORMAL_DISTRIBUTED_EVIDENCE_COMPLETE.json` | 最后写入的分布式完成标记 |
| `distributed_model_update_manifest_fragment.json` | 可直接用于七项 manifest 的第 7 项片段 |

云端存储目录包含：

| 路径 | 内容 |
|---|---|
| `cloud_publication.json` | 不可变发布清单 |
| `edge_receipts.json` | 持久回执库和 revision |
| `acks/{edge_id}.json` | 对该边缘返回的确认原件 |

## 接入七项统一门禁

把边缘输出的 `distributed_model_update_manifest_fragment.json` 中
`model_update_loop` 复制到七项 manifest。若 manifest 不在该输出目录，调整所有
相对路径并重新计算对应 SHA。然后运行：

```bash
python scripts/evaluate_competition_targets.py \
  --manifest /path/to/competition_targets_manifest.json \
  --output-json /path/to/competition_targets_result.json \
  --output-markdown /path/to/competition_targets_result.md
```

第 7 项现在同时要求：

1. 本地 package、release、apply、rollback 和本地完成标记；
2. 分布式主证据和分布式完成标记；
3. 云端发布清单与边缘逐文件记录完全一致；
4. 本地模型顺序为旧版→候选版→旧版；
5. 边缘回执与本地证据、发布 nonce 和文件清单完全一致；
6. 云端确认绑定同一 receipt SHA、publication SHA 和持久化 revision；
7. 云端地址不是回环地址，运行模式是真实 HTTP。

## 当前事实边界

仓库现在提供完整可运行的双机 runner、严格统一门禁和单元回归，但这不等于已经在
Jetson 与云服务器上产生正式测量结果。只有在目标 Git 提交合并后，使用两份真实
GGUF 在两台真实机器上执行以上命令，才能把第 7 项记为正式通过。
