# 当前交通边缘大模型前三项正式取证指南

> 当前状态：服务器和 Jetson 取证 runner 已实现，但当前仓库没有随附当前
> 提交的服务器正式结果和 Jetson 内存正式结果。因此第 1、2、3 项目前均不能
> 声称“已实机测并达标”；只有统一门禁对当次正式证据输出 `passed`，
> 才能改变该结论。

前三项必须拆成两次独立取证，不能在服务器上一次运行后同时填写三项：

1. 能力保持率与 TTFT：在同一台 GPU 服务器上，用同一冻结题集、同一流式协议依次测
   Qwen3.5 9B 和当前交通 0.8B；
2. 单次推理内存：在实际部署 Edge-Qwen 的 Jetson 本机单独测量。

这样既保证 9B 与 0.8B 的能力、TTFT 对比公平，也避免把 5070 Ti/3090 服务器的
内存占用写成“边侧内存”。两个结果使用各自真实的 `hardware_id`，最后只在七项
manifest 中合并证据引用。

## 共同约束

- 0.8B 必须是 `asset_catalog.json` 当前声明的 GGUF，文件名和 SHA-256 均会校验；
- 题集必须与冻结 metadata 的总数和分类数一致；
- 题集必须且只能包含 `math`、`code`、`natural_language_reasoning` 三类，且每类
  至少一题；
- 正式取证要求 Git 工作区干净、输出目录为空；
- 脚本不会安装、下载、训练、部署模型，也不会修改正式服务。

统一门禁还会重新核对能力证据中的三类分数、三类样本数和宏平均。只写一个总分，
或者数据与 metadata 一起删掉某一类，都会被判为“证据无效”。

## 第一次：服务器实测能力和 TTFT

入口：

```text
scenes/freeway_traffic/traffic_system/measure_current_edge_llm_targets.py
```

9B 与 0.8B 必须运行在同一台服务器，两个 HTTP 地址只允许 loopback。9B 还会校验
Ollama manifest、模型 blob 和运行时 `/api/ps` digest。

```bash
python scenes/freeway_traffic/traffic_system/measure_current_edge_llm_targets.py \
  --llama-server /实际路径/llama-server \
  --teacher-manifest /实际路径/qwen3.5/9b \
  --teacher-blob /实际路径/sha256-dec52a44569a2a25341c4e4d3fee25846eed4f6f0b936278e3a3c900bb99d37c \
  --dataset-jsonl /实际路径/general_capability_eval/eval.jsonl \
  --dataset-metadata /实际路径/general_capability_eval/metadata.json \
  --hardware-id 5070ti-server-same-protocol-v1 \
  --run-id current-edge-qwen-targets-1-2-20260809 \
  --output-dir /空目录/targets_1_2
```

输出：

- `targets_1_2_raw.json`：逐题输出、正确性、TTFT及模型/数据哈希；
- `capability_retention.json`：第1项证据；
- `ttft_reduction.json`：第2项证据；
- `targets_1_2_manifest_fragment.json`：只包含第1、2项。

这个入口不采集、也不输出正式内存证据。即使服务器内存看起来低于 1.5GB，也不能
用于第3项。

## 第二次：Jetson 本机实测单次推理内存

入口：

```text
scenes/freeway_traffic/traffic_system/measure_current_edge_llm_memory.py
```

将同一提交、同一 GGUF 和冻结题集放到实际边缘板后执行：

```bash
python scenes/freeway_traffic/traffic_system/measure_current_edge_llm_memory.py \
  --llama-server /实际路径/llama-server \
  --edge-model /实际路径/qwen35_0_8b_current_state_future_v2_q6_k.gguf \
  --dataset-jsonl /实际路径/general_capability_eval/eval.jsonl \
  --dataset-metadata /实际路径/general_capability_eval/metadata.json \
  --run-id current-edge-qwen-target-3-jetson-20260809 \
  --measurement-count 10 \
  --output-dir /空目录/target_3
```

脚本从 `/proc/device-tree/model`、系统架构和主机名自动生成硬件取证；不提供手填
`--hardware-id`。只有 `aarch64` 的 NVIDIA Jetson 能生成正式证据。每个观察窗只发
一次请求，记录进程树 VmRSS/PSS 峰值，再取多个独立观察窗中的最大 VmRSS 作为门禁值。

输出：

- `target_3_jetson_raw.json`：逐次请求的内存和时延原始记录；
- `single_inference_memory.json`：第3项证据；
- `target_3_manifest_fragment.json`：只包含第3项。

统一门禁要求内存证据同时满足：边缘角色、Jetson 平台、`aarch64` 架构、内核设备
型号、单请求观察窗以及正内存值。旧的一体式证据或服务器内存证据会被明确拒绝。

## 合并到七项总门禁

把两个 fragment 中的 `targets` 分别合并到完整七项 manifest：

- 服务器 fragment 提供 `capability_retention`、`ttft_reduction`；
- Jetson fragment 提供 `single_inference_memory`。

两类证据的硬件标识本来就应不同，不要改成相同字符串。证据路径若因移动 manifest
而变化，必须同步改路径并重新填写文件的实际 SHA-256。最后执行：

```bash
python scripts/evaluate_competition_targets.py \
  --manifest /完整七项manifest.json \
  --output-json /七项门禁.json \
  --output-markdown /七项门禁.md
```

能力保持率、TTFT降幅和内存是否达标只由统一门禁计算，测量脚本不提前写“通过”。
