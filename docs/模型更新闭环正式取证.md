# 边缘本地模型更新状态机取证

这项工具验证第 7 项中的边缘本地部分：模型打包、本地发布、边缘应用以及
失败自动回滚。它不修改正在运行的正式服务。单独完成本页流程不代表第 7 项
已通过；统一门禁还要求真实云边 HTTP 发布、下载、回执和云端确认。

入口：

- `scripts/measure_model_update_loop.py`
- 或 `python -m edge_llm_factory measure-update-loop`

## 实际执行了什么

一次正式取证固定执行以下顺序：

1. 校验旧版本和候选版本的 base manifest、适配器包、发布门槛、GGUF 大小与
   SHA-256；旧、候选 GGUF 的 SHA-256 必须不同。
2. 在输出目录内创建隔离的 `ReleaseStore`，将旧版本发布为 revision 1。
3. 在未占用的 loopback 端口实际启动旧 GGUF，等待 `/health`，再向
   `/completion` 发送一次真实的 1-token 推理探针。
4. 发布候选版本为 revision 2，实际停止旧进程、启动候选 GGUF，完成健康检查和
   一次真实推理。
5. 在候选已通过健康与推理探针后注入
   `post_health_inference_gate_failure`。这是只抛出异常的无损测试故障，不修改
   GGUF、package 或系统环境。
6. 由 `ActiveReleaseLlamaServer` 的正式故障路径调用
   `ReleaseStore.rollback_if_active()`，生成 revision 3，停止候选进程并重新启动
   旧 GGUF。
7. 再次验证旧模型健康、真实推理、进程命令行、GGUF SHA、registry revision 和
   runtime config 全部一致，随后停止这套隔离服务。

这不是“文件存在性测试”。正式成功需要看到三次真实启动顺序：

```text
旧模型 → 候选模型 → 旧模型
```

## 安全边界

- 只允许绑定 `127.0.0.1` 或 `localhost`，不会开放局域网端口。
- registry 和 runtime config 都写入新的输出目录，不读取或改写生产 registry。
- 输入资产只读，候选故障不会破坏模型文件。
- 输出目录必须不存在或为空，避免把旧证据混入本轮。
- 正式运行要求 Git 提交与 `--git-commit` 完全一致，并且工作区干净。
- 无论成功还是失败，脚本都会停止自己启动的隔离 llama-server。
- 机器必须有足够内存逐次完成三次串行模型加载；脚本不会与生产端口复用。

## 正式命令

下面的路径必须替换成目标边缘机器上的真实文件。`--probe-prompt` 应使用该模型
输入契约允许的固定短输入；原文不会写进证据，只记录 SHA-256。

```bash
python scripts/measure_model_update_loop.py \
  --repository-root /path/to/cloud-edge-scene-sdk \
  --git-commit "$(git rev-parse HEAD)" \
  --old-base /path/to/old/base_manifest.json \
  --old-package /path/to/old/adapter_package \
  --old-artifact /path/to/old-model.gguf \
  --candidate-base /path/to/candidate/base_manifest.json \
  --candidate-package /path/to/candidate/adapter_package \
  --candidate-artifact /path/to/candidate-model.gguf \
  --old-release-id edge-model-v1 \
  --candidate-release-id edge-model-v2 \
  --llama-server /path/to/llama-server \
  --host 127.0.0.1 \
  --port 19290 \
  --context-tokens 128 \
  --threads 4 \
  --gpu-layers 99 \
  --startup-timeout-seconds 90 \
  --probe-prompt '固定的短输入' \
  --fault-mode post_health_inference_gate_failure \
  --dataset-id update-smoke-v1 \
  --hardware-id edge-device-and-runtime-id \
  --run-id update-loop-YYYYMMDD-HHMMSS \
  --output-dir /path/to/new-evidence-dir
```

只想检查路径、包契约、SHA、Git 和端口时，加 `--dry-run`。dry-run 不创建输出目录，
不启动模型，也绝不会生成 `status=completed` 的四阶段文件或主证据。

## 输出文件

正式闭环全部验证成功后才会产生：

| 文件 | 含义 |
|---|---|
| `01_package.json` | 两个真实 package、base 和 GGUF 的校验结果与 SHA |
| `02_release.json` | 两次 promote 与最终 rollback 的 registry 历史 |
| `03_apply.json` | 旧模型和候选模型的真实 PID、命令行、health、推理探针 |
| `04_rollback.json` | 候选退出、旧模型恢复、revision 对齐和恢复后推理 |
| `model_update_loop.json` | 七项统一门禁读取的第 7 项主证据 |
| `FORMAL_EVIDENCE_COMPLETE.json` | 最后写入的本地完成标记，绑定主证据和四阶段 SHA |
| `model_update_loop_manifest_fragment.json` | 可复制到统一 manifest 的第 7 项配置片段 |
| `isolated_release_store.json` | 本轮隔离 registry 原件 |
| `isolated_runtime.json` | 回滚后的隔离 runtime config 原件 |

四个阶段文件写完后，主证据保存它们各自的 SHA-256。统一门禁还会重新读取文件并
复算 SHA；任一文件被修改，证据就会判为无效。

如果正式执行中途失败，只会留下 `FAILED_NOT_FORMAL_EVIDENCE.json` 和可能存在的
隔离诊断文件，不会生成主证据。单元测试使用 fake process 验证状态机，但
`_write_formal_evidence()` 会拒绝 `execution_mode=test_double`，因此单元测试不能
冒充真实部署结果。

## 接入七项统一门禁

本文件描述的是边缘机器内部的真实 apply/rollback 状态机。七项统一门禁现在还
要求“云端发布→边缘拉取→边缘回执→云端确认”的分布式证据，单独运行本页命令
不能再让第 7 项通过。正式双机取证请改用
[`云边模型更新闭环正式取证.md`](云边模型更新闭环正式取证.md)；它会调用本页
状态机，并自动生成包含两层证据的 manifest 片段。

不要把本地 `model_update_loop_manifest_fragment.json` 直接复制到七项 manifest；它没有
`distributed_evidence` 和 `distributed_completion_marker`，必然无法通过当前 schema。
完成双机取证后，应复制 `distributed_model_update_manifest_fragment.json` 中
`model_update_loop` 的内容。如果统一 manifest 不和该输出目录放在一起，需把其中
相对路径改为相对于统一 manifest 的路径，再重新计算对应 SHA。最后执行：

```bash
python scripts/evaluate_competition_targets.py \
  --manifest /path/to/competition_targets_manifest.json \
  --output-json /path/to/competition_targets_result.json \
  --output-markdown /path/to/competition_targets_result.md
```

只有 package、release、apply、rollback 四个文件都存在且 SHA 一致，候选模型 ID
与旧模型不同、回滚后模型 ID 恢复为旧模型，并且分布式发布与云端回执确认也通过
时，第 7 项才会通过。

## 当前事实边界

仓库现在具备边缘本地状态机 runner；这不等于已经在 Jetson 上完成一次
正式测量，也不等于已完成云边发布闭环。必须按双机取证文档在云服务器和
目标边缘机上执行，再由统一门禁输出 `passed`，才能把第 7 项改为“通过”。
