# 四路径多实验证据汇总

平均端到端时延按业务真正需要等待的终点统计，不要求一次正常联网运行自然出现
断网路径。四条路径分别做预注册实验，最后再按测量前锁定的正权重汇总。

当前仓库已提供预注册汇总器和统一门禁，但未随附当前提交、当前模型和目标硬件的
正式四路径输出。因此本页是取证指南，不是“第 5 项已实测或已达标”的结论。

## 口径

- `edge_only`：止于安全规则允许的本地 `provisional`；在线摘要仍必须已进入
  `handoff_durable` 或 `outbox_durable`，该策略名不表示禁止摘要上云。
- `local_autonomy`：止于本地安全 `provisional`，但摘要必须已进入
  `handoff_durable` 或 `outbox_durable` 持久队列，不要求断网时凭空产生云端
  `final`。
- `cloud_async`：止于已返回且带完整 action authorization 的安全 `provisional`，
  摘要也必须已进入 `handoff_durable` 或 `outbox_durable`。监测、告警、记录或
  明确授权的低风险动作可立即使用；需要云确认的高风险动作必须仍列在
  `deferred_action_types`，不能借 SLA 口径取得执行权。
- `cloud_sync`：始终止于权威 `final`。

因此，前三条路径的机器可核验终点统一写作
`provisional_response_and_durable_summary`；只有 `cloud_sync` 写作
`authoritative_final`。后台稍后取得的全局 `final` 可另行报告，不能反过来冒充
前三条路径都必须等待的业务端到端终点。

这里的“安全 `provisional`”有明确的失败关闭条件，不是只检查一个状态字符串：
`policy_wait=false`、`response_status=provisional`、动作授权合同存在，且
`response_actions` 必须完整覆盖无重复、无交集的 `immediate_action_types` 与
`deferred_action_types`。每个动作的 `requires_cloud_confirmation` 必须与所属集合
逐项一致；需云确认的动作不得被本地授权，允许立即执行的动作才可获得本地授权，
响应也不得声称已获云确认。三条路径还都必须声明摘要需要投递，并已到达可崩溃恢复
的持久阶段；`local_autonomy` 另须有本地自治标记。`cloud_sync` 则必须同时满足
同步等待、review 已完成、完成阶段可作为权威终点、状态为 `final`、云确认成立且
存在 `global_final_ms`，缺一项都记作失败。

分层只读取 benchmark 事件中的 `policy_route`。`delivery_route` 可能因
provisional-first 响应策略改变，只作为审计字段，不能用来冒充调度路径。

## 使用顺序

1. 复制 `schemas/four_route_e2e_experiment_plan.example.json`，在实验开始前固定
   权重、Git 提交、模型、硬件、数据 SHA、每次实验的样本、分区和网络 profile。
2. 先保存计划文件并记录其 SHA。每条路径可登记一个或多个 benchmark 结果文件，
   但不能在结果出来后删除慢样本或失败运行。
3. 每个 benchmark 结果旁保存一个运行证明文件。运行证明必须绑定结果 SHA，例如：

```json
{
  "schema_version": "1.0",
  "run_id": "offline-run-01",
  "experiment_plan_sha256": "预注册四路径计划SHA-256",
  "benchmark_sha256": "替换为实际结果SHA-256",
  "git_commit": "替换为实际提交",
  "dataset_id": "pems08-current-state-fixed-test-v1",
  "data_sha256": "替换为数据SHA-256",
  "model_ids": {
    "edge_student": "替换为模型SHA-256",
    "edge_qwen": "替换为模型SHA-256",
    "cloud_fusion": "替换为模型SHA-256"
  },
  "hardware_id": {
    "edge": "jetson02-orin-nano",
    "cloud": "server-5070ti"
  },
  "network_profile": {
    "profile_id": "cloud-outage",
    "cloud_available": false
  },
  "run_started_at": "2026-08-09T09:00:00+08:00"
}
```

`run_started_at` 必须与 benchmark 的 `measurement_started_at_utc` 完全相同，且
不能早于计划的 `locked_at`；`experiment_plan_sha256` 必须精确绑定测量前冻结的
计划。工具还会核对 benchmark 内的数据 SHA 和固定样本全集。

4. 汇总：

```bash
python scenes/freeway_traffic/aggregate_four_route_e2e_evidence.py \
  --plan 实验结果/四路径计划.json \
  --output-evidence 实验结果/四路径业务时延证据.json \
  --output-weight-plan 实验结果/四路径固定权重.json
```

5. 将两个输出文件及其 SHA 写入
`schemas/competition_targets_manifest.example.json` 对应的
`weighted_business_e2e.evidence` 和 `weight_plan`，再运行统一七项门禁。

## 防止挑数据

尝试数由计划中的 `sample_ids × partition_ids` 决定，不由结果文件中成功返回的行数
决定。缺文件、缺事件、路径未按计划命中、持久队列缺失或权威 final 缺失都会作为
失败保留。实际结果若多出未登记事件，会使该次运行的全部预注册尝试失效，防止先跑
大集合再挑快样本。输出文件已存在时汇总器拒绝覆盖，避免正式证据被静默替换。
统一门禁会从 `source_runs` 重建 `sample_id × partition_id` 分母，并按同一 run 内的
`sample_id` 聚类 bootstrap；证据自报的计数或任意 `group_id` 不能改变分母和聚类。
汇总器只生成证据，不自行宣布是否满足 200 ms；最终结论由
`scripts/evaluate_competition_targets.py` 给出。
